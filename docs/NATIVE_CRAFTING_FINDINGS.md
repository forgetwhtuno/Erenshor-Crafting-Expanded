# Native Erenshor Crafting/Forge Findings

Generated by reflecting/disassembling the installed game assembly directly (repo had **no** prior
crafting/forge evidence — checked `research/`, `ERENSHOR_REFERENCE_PACK_2026-08-10/`, `third_party/`,
`docs/`; all crafting-related content there was wiki-sourced prose, not code).

- Source: `<Erenshor install>\Erenshor_Data\Managed\Assembly-CSharp.dll`
  (the same installed game build this repo's other mods compile against).
- Method: reflection + a throwaway IL disassembly scratch tool (`ildump.exe`) — not checked into
  this mod. Regenerate the same way if these findings need re-verifying against a future game patch.
- Confidence: `[CODE]` for anything with a quoted type/field/method name below. Nothing here is
  paraphrased from the wiki.

## 1. Forge controller

`Smithing : UnityEngine.MonoBehaviour`, accessed via the static singleton `GameData.Smithing`.

Fields:
- `GameObject SmithingWindow` — the forge UI root; `SmithingWindow.activeSelf` is the authoritative
  "is the forge open" check (set `true` in `OpenWindow`, no explicit `false` assignment was found in
  `OpenWindow`/`CloseWindow` disassembly excerpts pulled so far — `CloseWindow()` itself wasn't
  disassembled this pass, treat its exact behavior as **unverified**, but `SetActive(false)` is the
  obvious inference for a "Close" method and is safe to rely on for a read-only gate).
- `ItemIcon Template` — the template/recipe-defining slot (quantity forced to exactly 1, see below).
- `ItemIcon FuelSource` — the fuel/coal slot (quantity forced to exactly 1, see below).
- `List<ItemIcon> Components` — the material ingredient slots. **Each slot's `ItemIcon.Quantity` can
  be > 1** — this is a real per-slot stack count, not a single-unit constraint.
- `ParticleSystem Success`, `Vector3 pos`.

Methods: `Start()`, `OpenWindow(Vector3)`, `Update()`, `CloseWindow()`, `Combine()`, `DoSuccess()`,
`SpecialCombine(ItemIcon)`, `SpecialDecombine(ItemIcon)`.

## 2. Recipe/template representation

There is **no separate "Recipe" data type**. A recipe is just an `Item` (a `BaseScriptableObject`)
with `Item.Template == true`, plus:
- `List<Item> TemplateIngredients` — the required ingredient list. Quantity of a given ingredient is
  encoded by **repeated entries of the same `Item` reference** in this list (e.g. "Iron Ore x3" is
  three identical entries), not a separate quantity field.
- `List<Item> TemplateRewards` — the output item(s). `DoSuccess()` only ever reads `TemplateRewards[0]`
  — **only a single output item type is ever produced per craft**, no evidence of multi-output recipes.

Fuel is a separate `Item.FuelSource == true` flag; `Item.FuelLevel` is an `Item.FuelTier` enum
(`one`..`five`) used by `DoSuccess()` to scale output quantity for non-equipment recipes (see below).

Two Template items have hardcoded special-case IDs in `Combine()` that bypass the generic
`TemplateIngredients` matching entirely and instead do direct item "blessing"/quality-upgrade
combination logic (`SpecialCombine`/`SpecialDecombine`): `Id == "31377423"` (a box requiring a
"Planar Stone", `Id == "46289586"`, as fuel) and `Id == "2298018"` (a diamond that removes a
blessing) and `Id == "2265228"` (a box that combines two matching "BLUE SPARKLING" i.e. blessed items).
**These are the game's existing item-quality-tier mechanics** (matches the wiki's "Merging Vessel" /
"Inert Diamond" quality-tier description) — this mod must not intercept or duplicate them; they are
out of scope (the user's boundary list excludes new quality/upgrade mechanics) and already native.

## 3. Ingredient/inventory representation

`ItemIcon` (the UI/data slot, used both in inventory and in the forge) has:
- `Item MyItem` — reference to the `Item` ScriptableObject occupying the slot, or `GameData.PlayerInv.Empty`
  (a sentinel `Item`) when empty.
- `int Quantity` — stack count for that slot.

There is no separate lightweight "stack" struct — `ItemIcon` itself doubles as the stack unit
everywhere (inventory slots, forge slots, loot slots, mouse-cursor slot).

## 4. Ingredient consumption on successful craft

`Smithing.Combine()` (the "Craft" button handler), generic-recipe path (reached when `Template.MyItem`
is any `Item` other than the three special-case IDs above):

1. **Hard, unconditional gate — before even checking the recipe**: if `Template.Quantity > 1` or
   `FuelSource.Quantity > 1`, `Combine()` logs an error ("Cannot use more than one template/fuel
   source item at a time.") and returns immediately. **Template and fuel are always exactly 1 unit.**
   This is enforced by the game itself, not by UI convention — a mod cannot safely bypass it without
   Harmony-replacing `Combine()` wholesale, which this mod will not do.
2. Validates `Template.MyItem.Template` and `FuelSource.MyItem.FuelSource` are both `true` ("Invalid
   template/fuel source...").
3. Builds a flat list of placed items by iterating `Components`, and for each non-empty slot, adding
   `ItemIcon.MyItem` to the list **`Quantity` times** (a `for` loop from 0 to `Quantity`). So a single
   `Components` slot holding `Iron Ore x3` expands to three list entries — **this is exactly the
   native multi-quantity consumption path the user asked about, and it already exists.**
4. Compares that expanded placed-list against `Template.MyItem.TemplateIngredients` (also expanded by
   its repeated-entry encoding): every required entry must be matched exactly once, and there must be
   zero leftover/unmatched placed entries, or it fails with `"Invalid recipe... Check items and
   quantities"`. **This means the player must place the exact required quantity in each Components
   slot — not "at least" that many.** Placing a whole 83-unit Iron Ore stack when the recipe needs 3
   fails validation (80 unmatched leftovers).
5. On full match: clears `Components[0]` (reused to hold the reward — see `DoSuccess`), clears
   `Template`/`FuelSource` back to `PlayerInv.Empty`, then calls `DoSuccess()`.

`Smithing.DoSuccess()`:
- Plays the success sound/particle and logs `"Item successfully forged!"`.
- Sets `Components[0].MyItem = Template.MyItem.TemplateRewards[0]` (the output item).
- If the output's `Item.RequiredSlot` is *not* `Primary` (16) or `Secondary` (17) — i.e. not a
  weapon — sets `Components[0].Quantity = FuelSource.MyItem.FuelLevel + 1`
  (`FuelTier.one`(0)→1 up to `FuelTier.five`(4)→5). **This is the native "fuel tier controls output
  quantity for stackable/consumable results" behavior** — the closest thing to a quality/tier lever
  the generic recipe path has. Weapon/armor outputs stay at whatever `Components[0].Quantity` already
  was (effectively 1, since the ingredient match required exact quantities that summed via one slot
  reused).
- Contains dead/vestigial logic that returns leftover `Quantity - 1` units of `FuelSource`/`Template`
  to inventory via `Inventory.AddItemToInv` — this can never execute in the generic path because step
  1 above already forces `Quantity <= 1` before `Combine()` ever reaches `DoSuccess()`. Documented as
  an anomaly, not a mechanism to build on.

**No explicit "output quality" field or enum was found on `Item`.** Item quality tiers (Standard /
Improved / Blessed / Ascended per the wiki) are represented as **distinct `Item` ScriptableObjects**
selected via `TemplateRewards`/the special-case blessing combine paths, not a numeric quality field
computed at craft time. A mod cannot "set quality higher" on a crafted item — it can only observe
which `Item` came out.

## 5. Output creation

`DoSuccess()` writes the output directly into `Smithing.Components[0]` (see above) — there is no
separate "spawn item" method; the forge slot itself becomes the output slot, and the player presumably
drags it out afterward via the same generic `ItemIcon` drag/drop the rest of the inventory UI uses.

## 6. Craft success/failure signal

No event/delegate exists. The **only reliable success signal is a Harmony postfix on
`Smithing.DoSuccess()`** — it is called exactly once per successful craft, only from the end of the
generic-recipe success path in `Combine()` (and not from any failure branch). This is the correct XP
award hook: it fires only after all matching/validation has passed, never on ingredient placement,
invalid recipes, or UI reopening (`OpenWindow` never calls `DoSuccess`). At postfix time,
`Smithing.Components[0].MyItem` is already the reward `Item` and `Smithing.Template.MyItem` has
already been reset to `Empty` — so **the Harmony patch must capture the recipe identity (Template's
prior `Item`) in a Harmony `__state` prefix**, not read it in the postfix.

## 7. Existing forge/crafting UI evidence

- `Smithing.SmithingWindow` (`GameObject`) — the forge panel itself (see §1).
- `ForgePresence : MonoBehaviour` — `OnTriggerEnter`/`OnTriggerExit` only, no fields found this pass.
  Strong inference (not yet body-disassembled) that this is a proximity trigger near forge world
  objects, analogous to the `"Forge"` Unity tag already known from `third_party/ErenshorCoop`. Treat
  as **unverified** until its method bodies are disassembled — do not build a hard dependency on it
  yet; the mod instead polls `GameData.Smithing.SmithingWindow.activeSelf`, which is confirmed.
- `ForgeEffect : MonoBehaviour` — just a `ParticleSystem Success` field, a companion VFX component,
  not a controller.
- `GameData.CraftWindow : Crafting` — a **separate, apparently unimplemented** type: `Crafting` itself
  (`UnityEngine.MonoBehaviour`) has **zero fields and zero methods** in the current build. Likely a
  stub for a future non-Smithing crafting station. Not usable; ignore for v1.
- `ItemIcon.QuickSmith()` — **directly relevant native helper**, invoked from the inventory item's
  context-menu-style quick-action dispatch (alongside `QuickBank`/`QuickSell`/`QuickBuy`/`QuickTrade`
  etc. on the same class). Moves **exactly 1 unit** of the clicked `ItemIcon`'s item into the
  appropriate forge slot:
  - If `Item.Template`: into `Smithing.Template` (only if that slot is currently empty), quantity 1,
    logs `"1 <name> moved to forge."`.
  - Else if `Item.FuelSource`: into `Smithing.FuelSource` likewise.
  - Else (a generic material): finds a `Components` slot already holding the *same* `Item` and
    `Stackable == true`, and **increments that slot's `Quantity` by 1**; if no matching slot exists,
    uses the first empty `Components` slot instead. Decrements the source `ItemIcon.Quantity` by 1
    (clearing it to `Empty` if it hits 0).
  - This is **the native, authoritative, already-correct mechanism for building up a Components stack
    from inventory one unit at a time** — it already respects native consumption semantics perfectly.
    The only "friction" it has is that the player must invoke it once per required unit.

## Decision gate outcome (per plan Step 0.6)

Native stack-splitting is **not unsafe** — it already exists and is exactly what `QuickSmith()` does.
The QoL feature this mod builds is: given a validated recipe and its `TemplateIngredients` requirement
counts (readable off `Smithing.Template.MyItem.TemplateIngredients` once a template is loaded), invoke
the *same* native `ItemIcon.QuickSmith()` call N times per required ingredient (matching inventory
`ItemIcon`s by `Item` reference) instead of reimplementing consumption. This never bypasses
`Combine()`'s validation and never touches inventory fields directly — it only automates repeated
clicks of a mechanism the game already ships. Template/fuel remain single-unit by hard native
constraint. The mod does not guess/select a recipe before a template is loaded; the player uses
native `QuickSmith()` once on a template/fuel stack (or normal UI handling) to place one unit, which
already removes the need to manually split those stacks.

## Current implementation alignment after source review

The reviewed source now follows the evidence above more closely:

- `CraftSuccessPatch` captures the active recipe in a `Smithing.DoSuccess()` **prefix** and calls
  progression/commission handling only in the **postfix**, so XP is awarded after the verified
  native success method rather than before it.
- `ForgeStackQolPatch` prefixes `Smithing.Combine()` only to fill the **missing generic component
  units** through native `ItemIcon.QuickSmith()` calls. Native `Combine()` still performs exact
  recipe validation, consumption, quality/special behavior, and output creation.
- Template/fuel single-unit constraints are not bypassed. The player can use native QuickSmith to
  move one unit from a stack into those slots; the mod does not rewrite their quantities.
- The three special template IDs already identified in the current IL (`31377423`, `2298018`,
  `2265228`) bypass auto-fill entirely so their special native combine/decombine/blessing paths
  remain untouched.
- Craftable-count calculation now uses total matching availability from inventory **plus currently
  loaded forge slots**, and is limited by template/fuel availability as well as repeated component
  requirements. Special combines report no generic count rather than pretending the normal recipe
  formula applies.

These changes still require a local compile against the user's current Unity/Erenshor references
and an in-game regression test using both the native Craft button and the configured hotkey.


### Reviewed stack-QoL guard

The reviewed `ForgeStackQolPatch` does not blindly move ingredients into every failed forge state.
Before invoking repeated native `QuickSmith()` calls it verifies that all already-loaded generic
Components belong to the active recipe and that none already exceed the recipe-required count. A
malformed forge setup is left untouched for native `Smithing.Combine()` to reject/explain. This is
a QoL precondition only; native `Combine()` remains authoritative.
